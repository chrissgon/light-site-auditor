# Spike: the 3G profile and Lighthouse through its Node API (T-aud-2)

- Date: 2026-09-30
- Lighthouse: 13.5.0 (`npm view lighthouse version` on 2026-09-30; pinned in `package.json`)
- Result: `npx tsx src/lighthouse.ts <fixture url> out.json` saves the raw JSON; `tests/profile.test.ts` runs the same on the fixture page.

## Decision

The auditor uses Lighthouse's own **`mobileRegular3G`** preset with Lighthouse's default **simulated** throttling, on Lighthouse's default mobile screen.

| Setting | Value | Meaning |
|---------|-------|---------|
| `rttMs` | 300 | round trip between phone and server, in milliseconds |
| `throughputKbps` | 700 | bandwidth, in kilobits per second |
| `cpuSlowdownMultiplier` | 4 | the phone's processor is emulated four times slower than the machine running the audit |
| `requestLatencyMs` | 1125 (300 × 3.75) | only for DevTools throttling; unused by simulation |
| `downloadThroughputKbps` / `uploadThroughputKbps` | 630 (700 × 0.9) | only for DevTools throttling; unused by simulation |
| `throttlingMethod` | `simulate` | Lighthouse loads the page once without throttling and simulates the 3G load from that trace |
| `formFactor` | `mobile` | 412 × 823 screen at 1.75 density (`screenEmulationMetrics.mobile` in Lighthouse 13.5.0) |

## Sources

1. Lighthouse 13.5.0 takes its presets from Lantern in `@paulirish/trace_engine` 0.0.65 (`lighthouse/package.json` pins that version; `lighthouse/core/config/constants.js` sets `const throttling = Lantern.Simulation.Constants.throttling`). The preset, as published: https://unpkg.com/@paulirish/trace_engine@0.0.65/models/trace/lantern/simulation/Constants.js (accessed 2026-09-30). Its comment says the preset "partially align[s] with WebPageTest's definition of 'Regular 3G'" and is meant to roughly match the Chrome UX Report's 3G definition (HTTP RTT of 300 to 1400 ms, downlink under 700 kbps).
2. The same file upstream, in Chrome DevTools: https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/models/trace/lantern/simulation/Constants.ts (accessed 2026-09-30); same `mobileRegular3G` values and factors (3.75 and 0.9).
3. Lighthouse's throttling documentation, for the methods: https://github.com/GoogleChrome/lighthouse/blob/v13.5.0/docs/throttling.md (accessed 2026-09-30). Simulated throttling is the default and "uses a simulation of a page load, based on the data observed in the initial unthrottled load"; the default mobile profile is 150 ms and 1.6 Mbps (slow 4G), not 3G, which is why the auditor sets the 3G preset explicitly.
4. For comparison only, Chrome DevTools' "Slow 3G" network preset: https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/core/sdk/NetworkManager.ts (accessed 2026-09-30): about 500 kbps each way and a 400 ms target round trip (2000 ms applied latency), with no CPU slowdown.

`tests/profile.test.ts` compares `src/profile.ts` with `throttling.mobileRegular3G` from the installed Lighthouse, so an upgrade that changes the preset fails the tests instead of silently changing every number.

## Why this preset and this method

- It is Lighthouse's own definition of 3G, so a reader can check it against a documented source, and it comes with a CPU slowdown; DevTools' "Slow 3G" throttles only the network.
- Simulation is Lighthouse's default and gives the same number for the same trace; DevTools throttling slows the real load and varies more from run to run (source 3).
- Assumption: a small business's visitor on a weak mobile connection is close to this profile. Nothing was measured on real visitors; M2 (real sites) is where that can be checked.

## What the spike found

- The Node API takes the preset directly: `lighthouse(url, { port, onlyCategories: ["performance"], formFactor: "mobile", throttlingMethod: "simulate", throttling: REGULAR_3G })`, with Chrome started by `chrome-launcher` at Playwright's Chromium (`chromium.executablePath()`), the same pairing perfectui-doc uses in `tests/helpers/lighthouse.ts`.
- The raw result records the profile in `configSettings.throttling`, so every report can say which profile produced its numbers from the JSON itself.
- The `performance` category is enough: it carries `network-requests` (every file with `resourceType`, `transferSize` and `resourceSize`), `total-byte-weight`, the load metrics (`first-contentful-paint`, `largest-contentful-paint`) and the diagnostics and insights about weight.
- On the fixture served without compression, each `resourceSize` equals the file's size on disk and `total-byte-weight` equals the sum of `transferSize`; `transferSize` adds the response headers.
- In 13.5.0 many older weight audits are "insights" (`image-delivery-insight`, `render-blocking-insight`, `cache-insight`, `document-latency-insight`, `font-display-insight`); `unused-css-rules`, `unused-javascript`, `unminified-css`, `unminified-javascript` and `total-byte-weight` are still diagnostics.
